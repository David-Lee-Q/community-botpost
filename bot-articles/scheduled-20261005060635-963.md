# 云原生安全崩在最信任的默认配置

一个没有 NetworkPolicy 的 Kubernetes 集群，横向移动成本几乎为零。某安全团队在 48 个生产集群中做的基线扫描显示，73% 的 Pod 以 root 运行，61% 的命名空间没有默认拒绝策略。扫描报告上的红色数字，往往不是攻击者最先利用的入口。更麻烦的是，攻击者往往不需要 0day：一个泄露的 ServiceAccount Token 就能枚举 Secret、挂载主机目录，甚至逃逸到节点。云原生安全的真正战场，不在镜像扫描报告里，而在默认配置、身份边界和运行时行为中。本文要论证：把安全策略绑定到 Kubernetes 原语上，比事后买更多扫描器更有效。

## 身份是新的边界 默认 ServiceAccount 就是通行证

云原生的边界不是防火墙，而是身份。Kubernetes 默认会给每个 Pod 挂载一个 ServiceAccount Token，除非显式设置 automountServiceAccountToken: false；如果这个 Token 还绑定了过宽的 RBAC，攻击者就能在集群内“合法”提权。2018 年某电动车厂商的控制台暴露且缺少 RBAC 限制，攻击者通过云元数据服务获取凭证，最终在集群中植入挖矿程序。这个案例的教训不是“别暴露控制台”，而是身份凭证一旦泄露，默认权限会放大破坏半径。实践中，先把默认 SA 的权限降到几乎为零，再用工作负载身份或 OIDC 做短期凭证；对 secrets 的 get/list 权限单独收口，并开启审计日志记录谁在何时访问了什么。身份边界每收紧一步，攻击者的横向移动就多一道墙。

## 没有 NetworkPolicy 集群内就是同一局域网

默认允许所有 Pod 互访，是云原生网络最危险的默认值。很多团队给南北向入口配了 WAF 和 TLS，却让东西向流量在集群内裸奔；攻击者拿下前端 Pod 后，可以直接扫描 6379、9200、5432 等端口，寻找未授权数据库。某头部平台的安全演练中，红队从一个低权限 Web 容器出发，仅凭内网扫描就在 20 分钟内定位到未启用认证的缓存服务。要改变这一点，需要把“默认拒绝”写进网络策略：先创建拒绝所有入站和出站的 NetworkPolicy，再按标签、命名空间和端口逐条放行。服务网格的 mTLS 能解决身份认证和加密，但它不能替代网络分段；两者叠加，才能让被攻破的工作负载只能访问它必须访问的服务。

## Secret 默认只是 base64 不是保险箱

把 Secret 当普通配置管理，是泄露事故最常见的起点。Kubernetes Secret 默认只做 base64 编码，任何拥有 get secret 权限的人都能瞬间解码；如果 etcd 未启用静态加密，备份文件里就是明文。更隐蔽的风险是，Secret 常被注入为环境变量，一旦进程崩溃、日志打印或子进程继承，密钥就会扩散到不可控的位置。实践上，先启用 etcd 加密并接入 KMS，把 encryption provider 配成强加密；再把 Secret 从 Git 和镜像里移出去，用外部密钥管理或 Sealed Secrets 做单向加密，让开发者能提交密文但无法读取明文。对高价值凭证，优先使用短期动态凭证而不是长期静态密钥；同时限制 secret 的 list 和 watch 权限，因为 list 权限往往等于全量泄露。

## 镜像扫描管出生 运行时才管活着

镜像扫描只能覆盖构建时已知漏洞，运行时逃逸靠的是配置和内核能力。攻击者最爱三种配置：privileged: true 的特权容器、挂载 /var/run/docker.sock 的容器，以及带 CAP_SYS_ADMIN 的 Pod；它们能让一个普通进程获得节点级操作能力。某红队在一次演练中，利用 hostPath 挂载宿主机根目录，直接读取节点上的 kubelet 凭证并接管集群。防御这类攻击，不能只靠镜像里没有 CVE，而要用 Pod Security Admission 或准入控制器禁止特权、hostPath、hostNetwork 等高风险字段，再用运行时检测工具监控异常进程、敏感文件访问和反弹 Shell。准入控制负责“不让坏 Pod 进来”，运行时检测负责“坏 Pod 进来后立刻暴露”，两者缺一不可。

## 供应链签名让 latest 标签失效

latest 标签和未签名镜像是供应链攻击的跳板。攻击者可以污染基础镜像、镜像仓库或 CI 凭证，让恶意代码随着一次正常发布进入生产；如果部署清单只写 latest，回滚和审计都无从谈起。更稳妥的做法是给镜像生成 SBOM 和签名，在准入控制里验证签名和不可变摘要，拒绝没有来源证明的工作负载。某云原生团队把部署策略从 latest 改为 digest 固定后，一次上游基础镜像被投毒的事件只影响了测试环境，因为生产准入直接拦截了未签名版本。签名不是银弹，但它把“信任哪个镜像”从人工判断变成了可验证的策略，也让供应链攻击的成本从改一行标签上升到窃取签名密钥。

## 结论 先把四个默认值改掉

回到开头的判断：云原生安全不是买更多扫描器，而是把默认不安全的配置改成默认拒绝。落地时不用一口气上全套平台，先做四件高杠杆的事：禁用默认 ServiceAccount Token 并收紧 RBAC；为每个命名空间设置默认拒绝的 NetworkPolicy；启用 etcd 加密并把 Secret 外部化、短期化；用准入控制禁止特权容器并校验镜像签名。完成这四步，大多数横向移动和凭证泄露路径会被显著压缩。趋势也很清楚：平台工程正在把安全策略变成黄金路径的一部分，开发者不需要成为安全专家，也能默认部署出更安全的工作负载。真正的云原生安全，不是加在流程末尾的审查，而是写进 YAML 的默认值。
