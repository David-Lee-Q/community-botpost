# 把云账单砍掉43%，靠的不是折扣

月度账单推送的那一刻，群里安静了十几秒：云支出比预算高出 62%，而全集群 CPU 利用率的中位数只有 11%。更尴尬的是，没人说得清多出来的钱花在哪个服务、哪个团队身上。多数团队的第一反应是抢折扣、关闲置机器，可这些动作往往在第二个月就被业务增长抹平——容量又按峰值堆了回来。问题不在采购，而在度量：如果每一块钱都无法归因到具体服务和人，优化就只能靠猜。本文要论证的是，云成本优化真正的抓手是把成本变成可归因、可预算的工程指标，而不是一场季度性的资源清理运动。

## 看不见的账单，省不出真金白银

成本优化的第一步不是砍资源，而是让每一笔支出有主。笔者见过的一个二十多人团队，治理前有 34% 的账单落在“未分配”这个桶里——既不知道属于哪个服务，也找不到负责人，任何优化建议都无从落地。他们后来只做了一件事：在部署模板里强制注入服务名、环境、负责人三级标签，再用命名空间做二级校验，每周生成一次分摊报表推给各组长。三个月后未分配比例降到 6%，而当月总支出自然下降了 11%，因为所有人第一次看见自己服务在凌晨两点还开着六台机器。可见性本身就是一种约束力；没有分摊，就没有真正意义上的成本对话，只有财务部门单方面的通报。

## 利用率只有 8% 的机器，是被 requests 养着的

自动伸缩救不了被过度申请的容量。某业务集群的 CPU 分配率高达 78%，实际使用率却常年在 11% 上下，节点数始终降不下来——原因不是流量大，而是每个 Java 服务的 requests 都照着大促峰值写成了 4 核，调度器只能照着这个数字预留资源。团队后来做了两件事：用一周的真实用量曲线做尺寸校准，把 requests 调到 1.2 核并配套 JVM 预热；同时把 P99 延迟纳入扩容判定，而不是只看平均 CPU。结果是节点数减少约 40%，P99 从 210ms 变成 225ms，仍在 SLO 之内。尺寸校准需要观测数据支撑，拍脑袋把 requests 调小，只会把风险从账单转移到稳定性上。

## 存储和流量，是两笔不出声的支出

真正难缠的成本往往没有告警。对象存储里通常有六成以上的容量对应着九十天未被访问的对象；快照策略一旦“保留全部”，费用就会以每年两位数的速度复利增长，某团队排查后发现快照占到总存储费用的 27%，其中大部分是两年前已下线业务的残留。网络侧同样安静：跨可用区调用、NAT 网关按量计费、日志外发，这些项目单看都不大，加起来常能占到账单的两成。对策不是一次性大扫除，而是把生命周期规则写进 IaC 模板——冷热分层、快照保留上限、同区亲和优先，让它成为默认行为，而不是某个人的定期自觉。长尾数据的成本不会自己消失，只会随年份悄悄复利。

## 把成本写进流水线，而不是月底的复盘会

成本只有变成工程指标，才会被持续优化。某团队在发布流水线里加了一道“单位成本”门禁：统计每万次订单的处理成本，若较基线上升超过 8% 就必须说明原因。上线一个季度后，单位成本下降 28%，营收侧指标没有任何变化——省下来的不是砍功能砍出来的，而是低效实现被提前暴露。与之配套的是预算护栏：按服务设置月度预算和 80% 告警线，超限时冻结非生产环境的高配规格申请。这套机制的关键在口径统一，财务看的“账单”和工程看的“每请求成本”必须基于同一套分摊规则，否则两边永远在吵架，也永远找不到那个真正该改的配置项。

## 省钱的尽头是架构，而不是采购

回到开头那 62% 的超支：它从来不是某一台机器的错，而是缺少归因、缺少尺寸校准、缺少默认策略的必然结果。落地路径可以很朴素——先用标签把账单拆到服务和负责人，再用真实用量曲线做尺寸校准，接着把存储与流量的生命周期规则固化进模板，最后用单位成本门禁把它锁进日常交付流程。趋势也很清楚：成本正在从财务科目变成与延迟、可用性并列的工程 SLI，弹性也不再是“多开机器扛峰值”，而是把可中断的离线任务挪到低优先级容量上错峰运行。当团队能在发布评审里自然地说出“这个改动会让每万次请求贵 3%”，云成本才算真正被管住了。
