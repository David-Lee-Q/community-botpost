# API网关别只做转发 3个指标守住生产

## 网关不是反向代理
一次大促压测中，某电商团队把 120 个微服务接口直接暴露给前端，结果 3 分钟内 429 错误占比升到 40%，5xx 占比接近 30%，根因并不是服务挂了，而是限流、鉴权、日志散落在各服务里，入口没有统一容量边界。API 网关常被误认为只是反向代理，但生产环境里它真正承担的是流量入口、安全边界和可观测基线。本文不堆砌功能清单，而是从三个可落地指标讲清楚：路由与限流如何设计、安全策略如何前置、可观测如何形成闭环，帮助团队把网关从“能转发”升级为“能守生产”。如果入口策略缺失，后端服务越完善，故障面反而越大。对中小团队而言，这往往比增加一台机器更优先。

## 路由与限流：把容量边界写进入口
路由与限流的核心不是“能不能调通”，而是把容量边界显式写进入口。某订单系统曾把全局 QPS 简单设为 2 万，看似充足，却忽略租户差异：一个大客户调用占 70%，小租户接口被拖慢。后来按三层限流改造：全局 2 万、租户 2000、关键接口 8000，并配合令牌桶做突发缓冲。上线后 P99 延迟从 800ms 回落到 120ms，错误率下降明显。这里的关键是限流对象要具体到租户、接口和来源，而不是只配一个总开关；同时要把降级响应、排队策略和重试上限写清楚，避免客户端无限重试把网关打满。限流值也不宜拍脑袋，最好结合压测基线、历史峰值和业务容忍度共同确定。

## 安全前置：鉴权、脱敏与防重放
安全前置的价值，在于把重复且容易写错的校验逻辑收敛到入口。很多团队把 JWT 解析、权限判断、敏感字段脱敏分散在 30 多个服务里，结果一次 token 校验规则变更就引发多处不一致。某支付接口在网关统一完成签名校验、时间戳防重放和手机号脱敏后，服务侧只需关注业务逻辑，安全代码量减少约 60%。更重要的是，入口可以统一记录异常请求来源、拦截高频撞库行为，并为审计提供一致字段。安全策略一旦分散，排查时就要在多个服务日志里拼线索；收敛后，网关就是第一道可验证防线。对多租户系统，还要把租户配额、IP 信誉和请求指纹纳入同一策略引擎。

## 可观测闭环：从日志到故障定位
可观测闭环决定网关是“黑盒”还是“治理中枢”。只记录访问日志远远不够，真正有用的是把 traceId、服务名、接口名、响应时间、错误码和限流命中情况串成一条链路。某团队在网关统一注入 traceId 后，一次超时问题从原来平均 45 分钟定位到 8 分钟：先看网关 P99，再按 traceId 找到慢服务，最后发现是下游数据库连接池耗尽。除了日志，还要配置 SLO：例如核心接口可用性 99.95%、P99 低于 200ms、5xx 低于 0.5%。指标、日志、链路三者对齐，故障才能从“感觉慢”变成可量化判断。没有 SLO 的告警容易变成噪音，有 SLO 的告警才指向业务影响。

## 灰度与回滚：让网关成为发布开关
灰度与回滚能力，是网关从稳定运行走向持续交付的关键。发布系统服务时，如果直接全量切换，一个配置错误就可能影响所有用户。更稳妥的方式是在网关按 header、用户标签或地域灰度 10% 流量，并绑定错误率、延迟和限流指标。某团队在一次接口版本升级中，灰度 5% 流量后发现 5xx 从 0.1% 升到 2%，立即自动回滚，避免影响扩大。这里要强调两点：灰度规则必须可解释，回滚动作必须可执行；否则网关只是观察工具，而不是发布安全阀。回滚后还要保留现场，包括请求样本、配置版本和指标快照，便于复盘。

## 结论：先做三件事
回到开头的问题：网关的价值不在转发本身，而在它能否把容量、安全和可观测变成可执行策略。落地时不必追求大而全，可以先从梳理入口接口并标注业务等级开始，再为核心接口配置租户级限流和降级响应，最后建立 traceId 与 SLO 看板。等基础闭环跑通，再逐步引入灰度、多协议、AI 流量识别等能力。未来 API 网关会更多承担多端接入、智能限流和跨服务治理，但判断标准始终一致：它是否让生产问题更早暴露、更快定位、更可控回滚。这些动作不依赖复杂架构，却能在早期拦住大多数入口级故障。
