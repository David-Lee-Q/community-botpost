# 网关延迟涨到38ms后，我们删掉了80%的插件

凌晨两点，值班同学花了90分钟定位一个502，最后发现是网关上第27个插件在作怪：一个两年前接入的响应体脱敏模块，在灰度实例上把大报文读超时了。这不是个案。我们统计过12个中型团队的网关配置，平均挂载19个插件，其中真正有明确owner的不到6个。API网关最初被引入的理由很简单：把鉴权、限流、灰度、日志这些横切关注点从几十个服务里抽出来，统一集中到一层。但集中这件事有惯性，收着收着，网关就成了全公司最不敢动的那个组件。这篇文章想论证一个不太受欢迎的观点：网关的能力边界应当由延迟预算和故障半径决定，而不是由「能不能做」决定；大部分网关事故，不是性能不够，而是职责过宽。

## 每加一个插件，故障半径就翻一倍

插件链的成本主要落在可观测性上，CPU 反而不是大头。我们对同一份路由做了三轮压测，环境是单节点 8C16G、1KB 请求体、开启长连接：纯路由转发跑到 2.4 万 QPS，P99 为 9ms；挂上 JWT 校验、限流和访问日志后降到 1.9 万 QPS，P99 为 14ms；再叠加响应体改写和协议转换，直接跌到 8600 QPS，P99 为 38ms。有意思的是，后面这两个插件是全公司共用的，但真正需要协议转换的业务方只有 3 个。不过性能损失还不是最要命的，真正的问题是当一个 502 出现时，你得在五层插件里逐层排查是谁改了 header、谁提前返回了响应。插件越多，链路里非业务逻辑的占比就越高，而日志里恰恰看不出是哪一层消耗了时间。所以给插件设两个必须满足的指标：必须有 owner 和下线日期，必须有独立的 trace span。没有 owner 的插件，本质上就是一笔无人负责的技术债。

## 限流和熔断，位置比算法重要

限流做在网关只能保护网关自己，保护不了下游。某次促销，网关按 IP 限流 100 QPS，看起来很稳妥，结果用户走的是同一个出口 NAT，整个办公网被限成了同一个配额；同时下游订单服务的真实瓶颈在数据库连接池，只有 20 个连接，网关的令牌桶对此一无所知，照样放行。合理的做法是分层：网关做粗粒度的租户级、接口级配额，用滑动窗口挡住突发流量；服务侧用并发信号量做细粒度自保，因为只有它自己知道还剩几个连接。熔断必须放在离依赖最近的地方——网关只看到「这个路由 5xx 变多了」，分不清是下游挂了还是上游超时传导过来的。也正因为如此，网关上的自动重试要格外克制：一次 3 次重试乘上 5 层调用链，等于 243 个请求砸向已经快挂的库存服务，这是雪崩最经典的加速器。

## 配置进 Git，但别让网关变成配置中心

网关的配置要能进 Git、能灰度、能回滚，但不要让它承载业务规则。我们把路由从控制台手动点击迁移到声明式配置加 CI 校验之后，变更失败率从 7% 降到 0.8%，回滚时间从 20 分钟缩到 90 秒。反例同样明显：有团队把 AB 实验的分流比例、活动白名单、临时开关全塞进路由匹配条件里，结果一次运营改配置要走一次网关发布，审批链拉长到 3 天，网关版本号一周涨了 40 个。经验是把配置分成两类：路由、认证策略、配额这类低频且影响面大的，进 Git 走评审；高频变化的业务开关交给配置中心或特性开关服务，网关只做一层薄薄的透传，不做判断。

## 可观测性没法事后补

网关是唯一能看到全部南北向流量的地方，也是最容易形成监控盲区的地方。三件事必须在第一次上线前就做完：统一注入 trace id 并贯穿到服务，否则调用链会断在最外层，后面所有排查都只能靠猜；指标按路由维度而不是按实例维度打点，QPS、P99、4xx/5xx、上游 RT 都要能下钻到单个路由，不然一个慢路由拖垮整个实例时，你只能看到整体抖动；把日志采样策略写进 SLO，2 万 QPS 下全量访问日志每天是 TB 级，采 1% 足够定位趋势，但错误请求必须 100% 采样，否则复现成本会高得离谱。

## 结论：先划边界，再谈能力

回到开头那个 90 分钟的 502。真正拖慢定位的，不是某个插件写错了，而是没人能说清网关到底该负责什么。落地建议可以分三步走：先把插件盘一遍，每个都指定 owner 和过期时间，半年无人认领的直接下线；再把延迟预算写进架构评审，网关侧 P99 超过 10ms 的新增能力必须走评审；最后把边界写进规范——认证、路由、粗粒度限流、流量镜像归网关，业务规则、细粒度熔断、数据格式转换归服务。趋势上，网关正在向两端分化：南北向流量网关越来越薄，只做接入和治理；东西向的细粒度策略则逐步下沉到边车。如果现在还把网关当万能中间件用，两年后大概率要做一次代价更高的拆解，而那次拆解，往往是在一次故障之后被迫开始的。
