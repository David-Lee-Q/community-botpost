# 别再把 AI Agent 当企业聊天助手

一家制造企业上线 AI Agent 三个月，工单平均处理时长只降了 11%。复盘发现，Agent 能读知识库、能总结历史记录，却不能改 ERP 字段、不能发起审批、不能回滚错误操作。它被塞进 IM 对话框，成了更聪明的搜索框。Gartner 预测，到 2028 年 33% 的企业软件会内置 agentic AI，而 2024 年这一比例不足 1%。数量会暴涨，但多数企业会卡在同一处：把 Agent 当聊天助手，而不是流程执行者。AI Agent 重塑企业工作流的关键，不是模型多强，而是企业愿不愿意把流程控制权切成权限、状态和评估三件事，交给 Agent 执行。

![AI Agent 接入企业系统执行任务](https://images.unsplash.com/photo-1504384308090-c894fdcc538d?w=800&q=80)

## 从副驾驶到数字同事，差的是执行权

Agent 如果不能调用写接口，价值上限就是检索。某头部电子制造企业把采购异常处理 SOP 拆成 12 个节点，Agent 接管其中 7 个：读取物料交期、比对合同价、校验库存、生成通知、创建工单等。这些节点可逆、可校验，平均处理时长从 40 分钟降到 8 分钟。但改价、付款、供应商准入等 5 个节点仍保留人工审批。这个案例说明，重塑工作流不是让 Agent 一键替人，而是按风险分层授予工具权限。只读工具、建议工具、可逆写工具、不可逆写工具必须分开审批。否则 Agent 越能干，企业越不敢用。

## 流程不是提示词，是状态机

企业流程天生带有状态、超时、补偿和审计。报销审批有提交、校验、主管审批、财务复核、打款、归档等状态；任何一步失败都要知道从哪继续，而不是重新问一遍大模型。把 SOP 写成提示词，只能处理 happy path。真正可上线的 Agent 需要嵌入事件驱动状态机：每一步有输入 schema、输出 schema、幂等键、超时策略和补偿动作。比如发票验真失败，Agent 应回退到待补充而非直接拒绝；付款失败，要触发通知和重试队列。没有状态机，Agent 只是概率生成器；有了状态机，它才是流程执行器。

## 多 Agent 不等于多个人

不少团队把 Agent 分成产品经理、开发、测试等角色，仿佛人多力量大。但企业里多 Agent 的核心不是角色扮演，而是权限与上下文隔离。某云平台内部测试显示，把 5 个 Agent 串成流水线，如果没有共享状态和仲裁者，错误率会随步骤增加而放大。有效做法是设置一个编排者负责路由、合并与冲突裁决，其他 Agent 只拿到完成任务所需的最小上下文。共享记忆要区分事实、假设和临时结果，避免一个 Agent 的幻觉污染整条链路。多 Agent 的收益来自分工后的校验，而不是数量本身。

## 先算回滚成本，再算提效

企业落地 Agent 的最大阻力通常不是技术，而是责任边界。审计会问：谁批准了这次操作？数据从哪来？出错谁负责？因此选场景时，先算回滚成本，再算节省工时。低频、高价值、可逆的场景最适合起步，比如客服摘要、工单分类、发票初审、合同条款比对。指标也不能只看省了多少人天，要看一次通过率、人工接管率、例外率、平均恢复时间。某银行把 Agent 用于反洗钱初筛，可疑交易误报率下降约三成，但人工复核仍保留，因为监管要求最终责任在人。提效是结果，可审计才是入场券。

回到开头那家制造企业，问题从来不是 Agent 不够聪明，而是它没有被放进流程的控制结构里。AI Agent 重塑企业工作流，本质是把人操作软件改成 Agent 调工具、人管例外。落地建议只有一条：选一条端到端流程，画出状态机，定义工具权限，设置回滚与评估，先让 Agent 做只读和可逆动作，再逐步开放写权限。未来两年，企业软件会从菜单加表单，转向意图加工具调用；流程拥有者也会多一个新头衔——Agent 编排师。谁先完成这一步，谁就能把 AI 的提效从演示变成利润。
