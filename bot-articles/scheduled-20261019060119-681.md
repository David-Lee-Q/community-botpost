# 99%的云安全失败，都写在那份YAML里

Gartner 有一个被引用到近乎烂俗的判断：到 2025 年，99% 的云安全失败由用户自己负责。这句话之所以站得住，是因为云原生把大量默认配置的决策权交还给了使用者——而 Kubernetes 官方文档自己就写明，默认配置不是一个安全边界。一个把 API Server 暴露在公网、Pod 自动挂载 ServiceAccount Token、容器以 root 运行的集群，从被扫描到被植入挖矿程序，往往只隔着一个脚本的执行时间。真正的矛盾在节奏上：业务发布已经以分钟计，安全评审却还停留在上线前一周的表格里。本文要论证的是，安全不是买一个组件挂上去，而是要把控制点拆开，塞进镜像、YAML 和运行时这三条链路。

![配图1：云原生集群默认配置暴露出的攻击面](https://images.unsplash.com/photo-1467232004584-a241de8bcf5d?w=800&q=80)

## 默认配置是最大的一块攻击面

Kubernetes 的开箱配置优先解决的是能不能跑起来，而不是跑得安不安全。CIS Kubernetes Benchmark 给出的检查项超过一百条，覆盖控制平面、etcd、kubelet、网络与策略，其中相当一部分属于默认即不安全的范畴。kubelet 的 10250 端口若开着匿名认证，任何人都能列出 Pod、甚至 exec 进容器；etcd 没启用 TLS 和客户端认证，等于把整个集群的状态数据库对外开放。CNCF 的年度调查里，配置错误长期排在容器安全风险的首位。策略层面同样如此，PodSecurityPolicy 被弃用后由 Pod Security Admission 接手，restricted 级别要求禁止特权、禁止 root、禁止 hostPath，但默认的 namespace 并不会自动启用它，需要手工打标签。所以第一步往往不是采购，而是把 restricted 准入和基线扫描真正接进集群。

## 镜像和供应链是最脏的一个入口

镜像一旦推进仓库，就等于把别人写的代码连带依赖一起搬进了生产环境。常见的基础镜像为了兼容性塞进编译器、包管理器和完整 shell，体积上百 MB，跑一次扫描出来几十个高危 CVE 是常态；更麻烦的是构建时顺手把 .npmrc、.git、私钥一起 COPY 进去，这些内容在镜像层里永远擦不掉。配合 latest 标签、直接拉公共仓库、registry 只走明文 HTTP、不做签名校验，几件事凑在一起，等于给供应链投毒留了一扇门。可行的收敛路径是：多阶段构建只拷贝运行产物，用 distroless 或最小基础镜像压缩攻击面；在 CI 里强制扫描并阻断可修复的高危项；生成 SBOM 记录依赖来源；再用类型于 cosign/Sigstore 的方案做签名，在准入控制器里校验签名和摘要，拒收未签名镜像。这里的取舍在于卡的力度，把所有高危都设成阻断，流水线会被基础镜像拖死，通常先卡住可修复且已有在野利用的那部分，其余进入基线清单滚动清理。

## 运行时逃逸，靠审计日志是抓不住的

容器不是虚拟机，共享内核意味着逃逸一旦成功，边界就彻底消失了。runc 历史上多次出问题，CVE-2019-5736 可通过恶意镜像覆盖宿主机的 runc 二进制，2024 年的 CVE-2024-21626 又因文件描述符泄漏，让容器能够读到宿主机的文件系统，这些漏洞的影响面覆盖了绝大多数集群。再叠加把 docker.sock 挂进容器、开启特权模式、以及 hostPID 与 hostNetwork，基本等于把宿主机直接交出去。审计日志只能事后回看，行为检测才可能当场拦下。eBPF 的普及把内核态行为采集的成本压了下来，可以围绕进程、文件、网络三个维度建基线：某个只该处理 HTTP 的容器突然去读 /etc/shadow，或者发起对集群外部 25 端口的连接，就该告警甚至直接杀掉。检测规则不必一开始就写满，先把几条高价值行为跑通、把误报压下来，比堆一百条没人看的规则有用得多。

## 凭证与网络策略决定爆炸半径

横向移动的燃料，是过宽的 RBAC 和默认全通的网络。CI/CD 拿着 cluster-admin 的 kubeconfig 做发布、ServiceAccount Token 自动挂载且长期有效、业务 namespace 里能 list 全部 Secret，这些在真实集群里非常普遍。红队复盘的典型路径就是：拿下一个 Pod 里的 token，列出其他 namespace 的 Secret，找到镜像仓库口令，然后转头去投毒新镜像。兜底做法并不复杂，给每个工作负载单独建 ServiceAccount，只授予具体动词和资源，关掉自动挂载；NetworkPolicy 默认拒绝、按真实调用关系放行，很多 CNI 支持它却默认不开启，必须显式配置；服务间身份用 mTLS 加 SPIFFE 这类可验证身份，而不是依赖 IP 段和静态密钥。审计上要重点盯权限变更和 token 创建这两类记录，它们通常比异常流量更早暴露问题。

## 把四道闸门装进流水线，而不是挂在墙上

99% 的失败源于使用者，换个角度看，主动权同样在使用者手里。把控制点归拢，其实就四道闸门：镜像层做最小化、扫描与签名；配置层打开 restricted 准入、接入策略准入控制器与 CIS 基线；运行时用 eBPF 建行为基线和响应动作；身份与网络层落实最小权限、默认拒绝和双向身份校验。不必一次全上，先做三件成本最低的事就能挡掉大部分自动化攻击：把 API Server 和 kubelet 从公网摘下来，给生产 namespace 打开 restricted 准入，把 CI 所用 ServiceAccount 降权并禁用 token 自动挂载。趋势已经比较清楚，安全预算正从边界设备转向身份与配置的自动化校验，谁能把这些校验前置进发布流水线，谁就能在保住发布速度的同时，把出事之后的爆炸半径压到最小。
