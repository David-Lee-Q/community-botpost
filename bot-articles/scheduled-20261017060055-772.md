# 吞吐量最高的MQ，为什么让我们丢了订单

## 一次延迟抖动，暴露了三年前的选型决策

去年双十一凌晨，某电商团队监控大屏上，订单系统的 P99 延迟从 6ms 一路冲到 900ms，而消息队列集群的 CPU 使用率只有 12%——机器很闲，业务在丢单。事后复盘，问题不在容量，而在三年前选型时被一笔带过的那个决定：为了追求「单集群百万 TPS」的漂亮数字，他们选了吞吐最高的那款 MQ，并把所有业务塞进了同一套集群。这场事故的核心不是技术选错，而是选型逻辑错了——他们拿性能排行榜当了决策依据。本文想论证的是：消息队列选型从来不是比谁快，而是把投递语义、延迟形态、堆积能力和运维成本，与自己的业务 SLA 做一次精确匹配；只看吞吐量，等于只看冰山一角。

## 吞吐量是最好测的指标，也是最容易骗人的指标

吞吐量高，往往是用延迟和复杂度换来的。Kafka 的单机吞吐能做到几十万条每秒，靠的是顺序写盘加批量发送——生产者攒够一批再发，broker 顺序追加。批量越大吞吐越高，但单条消息的端到端延迟也随之从毫秒级涨到几十甚至上百毫秒。RabbitMQ 的单队列吞吐只有前者的零头，却能把延迟稳稳压在个位数毫秒，因为它逐条路由、逐条投递。某券商做过一组内部实测：同一份行情数据，用批量攒批的方案做逐笔风控，P99 延迟从 8ms 升到 210ms；而把 batch 调到 1 之后，吞吐直接掉到原来的七分之一。这不是产品缺陷，是设计取舍。所以选型的第一问不该是「它每秒能扛多少条」，而是「我的业务能容忍多慢」。延迟敏感型业务（风控、实时定价、工控指令下发）和吞吐敏感型业务（日志采集、埋点、离线同步），答案完全相反。

## 投递语义，决定你半夜能不能睡着

消息重复和丢失带来的损失，往往比「慢」高出几个数量级。至少一次投递意味着消费者可能收到重复消息，至多一次意味着可能丢，精确一次听起来完美，代价却是事务开销和吞吐下降。Kafka 从 0.11 起支持幂等生产者和事务，RocketMQ 用事务消息解决本地事务与消息发送的一致性，Pulsar 也提供事务能力——但再强的语义保证，也挡不住「消费端没做幂等」这一刀。某支付平台曾出现一次重复扣款事故：上游生产者因网络抖动重试，下游消费者把同一条消息处理了两次，而扣款接口没有基于业务流水号去重。金额不大，排查花了 6 小时。真正的结论是：不要把幂等寄托在 MQ 的语义声明上，它应该是消费端的第一行代码；再根据失败重试的成本，决定是「允许重复」还是「宁可丢弃」。

## 差距在故障时刻才显现，堆积与运维是真成本

平时看不出差别，出事时 MQ 的性格就暴露了。Kafka 把消息写进磁盘并保留多份，积压千万条也不会阻塞生产者，消费者追上进度只是时间问题；而部分内存型 MQ 在队列积压到阈值后会触发换页甚至阻塞生产端，反压一路传导到业务入口，把小故障放大成大面积不可用。运维复杂度同样被严重低估：Kafka 需要管理分区、副本与再平衡，一次分区扩容就可能触发全集群 rebalance；Pulsar 用存算分离缓解了扩容和堆积问题，却引入了 Broker、BookKeeper、元数据存储三套组件。某制造企业只有 3 名运维工程师，一次分区调整让消费停滞了 40 分钟，产线数据延迟上报。选型时必须算这笔账：三年 TCO 里人力成本常常超过机器成本，3 人团队和 30 人团队能驾驭的组件复杂度完全不同。

## 按场景查表，而不是按跑分排名

把选型问题还原成业务问题，答案会清晰很多。日志采集、埋点、流式计算这类「高吞吐、可容忍秒级延迟、允许少量重复」的场景，适合顺序写盘能力强、生态成熟的方案；订单、支付、库存这类「低延迟、强一致、需要事务」的场景，更适合原生支持事务消息和定时/延迟消息的产品；设备数据接入这类海量连接、小报文、需要 QoS 分级的场景，MQTT 协议族才是主角，常见做法是在边缘侧用 MQTT broker 收敛，再桥接到中心侧的流式管道；多租户 SaaS、十万级 topic 的场景，存算分离的架构优势才真正体现。除了功能匹配，还要看两件事：团队对现有技术栈的熟悉度，以及社区活跃度——没人踩过坑的组件，踩坑成本会成倍放大。某工业互联网团队的做法值得借鉴：先用两周做 PoC，用真实流量压测延迟、堆积恢复时间和故障切换表现，再决定，而不是看 GitHub Star 数。

## 结论：先写 SLA，再选组件

回到开头那个丢单的夜晚，真正的问题不是选了吞吐最高的 MQ，而是没人写下业务对延迟、可靠性、有序性的具体要求。落地建议很朴素：第一步，和业务方一起把 SLA 写清楚——P99 延迟上限、可接受的消息丢失率、是否需要严格有序、峰值倍率是多少；第二步，用真实流量做 PoC，重点观察故障注入后的恢复时间，而不只是稳态吞吐；第三步，把三年的人力、机器和迁移成本折成一张表，让决策者对代价有感知。趋势上，存算分离正在成为主流架构，消息与流计算的边界也在模糊，未来「选 MQ」很可能变成「选一条数据管道」。但无论形态怎么变，那句老话依然成立：没有最好的消息队列，只有最匹配的那一个。
