# 云原生安全四道防线堵住运行时风险

## 上线前没做，运行时才暴露

一次生产扩容，某个镜像被重新拉取，旧版本漏洞又被带进集群；服务网格开启后，原本不可达的内部接口突然暴露；安全团队发现告警时，流量已经跑了四十分钟。类似场景并不罕见：容器化交付速度越快，边界越模糊，传统“先扫描、后上线”的线性流程越容易失效。云原生环境里，安全不是上线前的一次检查，而是从构建、部署、运行到审计的持续控制。若只把安全放在发布门禁，就会把动态扩缩容、服务互信、密钥轮转等真实风险留在运行时。更麻烦的是，镜像、编排、网络、身份分属不同团队，责任容易断档，最后变成“谁都管一点，谁都不兜底”。对工程团队来说，真正的问题不是缺少工具，而是缺少一套贯穿交付链路的默认规则。

## 镜像不是终点，供应链才是起点

云原生安全的第一个断点，是只查镜像漏洞而不管供应链来源。某团队统计 120 个生产镜像，发现 17 个来自个人仓库，其中 5 个无法追溯构建参数；一旦上游基础镜像被污染，下游服务会在无感知的情况下继承风险。真正有效的做法，是把镜像当作可审计的软件制品：构建过程必须记录依赖版本、构建参数和签名信息，并让每个镜像都能回答“谁构建、用什么源码、依赖哪些组件”。在此基础上，SBOM 不是额外报表，而是后续漏洞响应、合规审计和快速隔离的基础。没有来源可信的镜像，再多的漏洞扫描也只是在不确定上打补丁。工程团队应把签名、来源校验和依赖锁定纳入构建流水线，让不可信镜像在部署前就被拒绝，而不是在运行时才暴露问题。

## 运行时检测要能回答“谁在访问谁”

运行时安全的核心不是抓异常进程，而是回答“谁在访问谁、用了什么凭据、是否符合策略”。某次演练中，一个测试容器通过共享节点网络访问了生产数据库，耗时 3 分钟被人工发现；如果服务之间没有身份边界，这种越权访问很难靠日志回溯。云原生环境里，容器生命周期短、网络动态变化，传统主机边界几乎失效，必须把身份和策略下沉到服务调用层面。通过默认拒绝、最小权限和策略即代码，可以把“允许哪些服务访问哪些端口”变成可版本化、可回滚、可审计的规则。这样，安全不再依赖运维人员临时封 IP，而是由系统持续执行。进一步看，服务网格、网络策略和访问控制需要共享同一套身份模型，否则策略会散落在不同配置里，最终变成难以维护的规则堆。

## 密钥和凭据是最容易被低估的风险

很多团队把安全重心放在漏洞和入侵，却低估了密钥与凭据泄露。某次事故中，一个过期 token 被提交到代码仓库，导致内部 API 被调用 2 万次；由于权限过大，攻击者可以横向读取多个服务的数据。云原生系统天然依赖凭据完成服务发现、配置拉取和身份认证，一旦凭据长期有效、作用域过宽，单点泄露就会变成系统级风险。更稳妥的路径是缩短凭据生命周期，把长期密钥换成短期令牌，并按服务、环境、操作类型限制作用域。同时，密钥访问必须进入统一审计，让每一次读取、轮转和异常调用都能被追踪。安全不是把密钥藏起来，而是让密钥即使泄露也“不值钱”。对平台团队而言，凭据治理应和代码审查、发布审批放在同一流程里，避免“先上线、后补权限”的惯性。

## 结论：把安全变成交付默认值

云原生安全的最终目标，是把安全变成交付默认值。回到开头的问题：风险不会停在发布门禁，而会随扩缩容、服务互通和凭据轮转持续变化。工程团队可以先把安全变成默认规则：镜像必须可追溯并签名，服务默认拒绝未知调用，凭据必须短期化且可审计。这三项不需要复杂平台，却能把最常见的越权、污染和泄露风险压下来。未来，云原生安全会进一步从“事后检测”转向“持续验证”，安全策略、可观测性和交付流水线将更紧密地耦合。对团队而言，真正要建设的不是更多工具，而是一套能持续回答“谁可以做什么”的默认安全秩序。
